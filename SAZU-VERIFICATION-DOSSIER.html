1 Introduction

1.1 Purpose

This document specifies the functional and non-functional requirements for SAZU (Self-Authenticated Zone Update) as built: the plugin/sazu CoreDNS plugin, its sazuctl client and sazu-watchd monitoring daemon, and the small set of CoreDNS-core (core/dnsserver, plugin/pkg/doh, plugin/pkg/dnsutil) extensions built to carry it over HTTPS. Every requirement below is drawn from what the code and its own governing comments actually assert, cross-checked against the RFCs it cites — this is a specification recovered from an implementation, not the other way around.

1.2 Scope

In scope: authentication and authorization of zone-content pushes; DNSSEC content signing and serving; key lifecycle (pinning, rollover, custody); the wire carriers a push may arrive over; operational controls (rate limiting, audit trail); and the separate delegation-change watch daemon. Out of scope: general DNS query performance/caching, and CoreDNS's own unrelated plugin ecosystem.

1.3 Conventions

Requirement statements use SHALL / SHALL NOT for mandatory behaviour and MAY for optional behaviour, in the sense of RFC 2119. Each requirement carries a stable identifier (AREA-NN), its source (a design-doc section, an RFC, or a documented engineering decision), and the test case(s) in the companion Test Specification that verify it.

2 System overview

SAZU is a split-signing DNSSEC scheme: a customer's own signer holds the zone's private key and never transmits it; the server accepts only already-signed zone content, delivered as an RFC 2136 dynamic UPDATE authenticated end-to-end by a SIG(0) transaction signature. A single Ed25519 key, flagged as a KSK, serves both roles — SIG(0) transaction signer and DNSSEC signer — so there is no separate account, API key, or out-of-band handshake. The first UPDATE for a zone ("first contact") is validated by walking the real DNSSEC chain of trust from the root down to the zone's delegating parent; once a key is pinned this way, every later UPDATE is checked by signature alone, unless it is a key rollover, which re-runs the same chain check for a new candidate key.

The system comprises four deployable pieces: the sazu CoreDNS plugin (server), sazuctl (customer-side push client), sazu-watchd (standalone delegation-change monitor), and a small set of upstream CoreDNS-core extensions that let the push arrive over HTTPS/HTTP3 as well as UDP/TCP.

3.1 AUTH — SIG(0) transaction authentication

IDRequirementSource
AUTH-01The server SHALL authenticate every RFC 2136 UPDATE using SIG(0) computed over the exact wire bytes as transmitted, never a re-encoding of the parsed message.RFC 2931 · §9.1/§10.1
AUTH-02The server SHALL reject an UPDATE with a missing, malformed, expired, not-yet-valid, or cryptographically invalid SIG(0) with RCODE NOTAUTH.RFC 2931
AUTH-03The server SHALL obtain the literal request wire bytes independent of transport: UDP/TCP via socket-read capture; HTTPS/HTTP3 via request-context propagation.§7.2/§7.3
AUTH-04If no wire bytes can be recovered for a request, the server SHALL fail closed with RCODE SERVFAIL rather than authenticate against a re-encoding.Engineering decision

3.2 CHAIN — First-contact chain of trust

IDRequirementSource
CHAIN-01On first contact (no key yet pinned for the zone), the UPDATE SHALL carry exactly one candidate DNSKEY at the zone apex.§10.2
CHAIN-02The candidate key's SIG(0) SHALL verify before the key may be pinned.§10.2
CHAIN-03The server SHALL walk the DNSSEC chain of trust from a hardcoded root anchor to the zone's delegating parent, verifying every DNSKEY/DS RRset and RRSIG traversed, and confirm at least one parent-published DS matches the candidate key.RFC 4034/4035 · §10.2
CHAIN-04First contact SHALL be refused (REFUSED, status ERR_NO_DS_PUBLISHED) if the parent publishes no DS for the zone at all.§12
CHAIN-05First contact SHALL be refused (REFUSED, status ERR_UNKNOWN_SIGNER) if a DS is published but none matches the candidate key.§12
CHAIN-06A first-contact UPDATE that does not also establish a real SOA at the apex SHALL be rejected (FORMERR) without pinning any key.Engineering decision
CHAIN-07The chain-of-trust check MAY be disabled per instance (insecure_skip_chain_validation) for non-production testing only.Operational

3.3 KEY — Key pinning & rollover

IDRequirementSource
KEY-01Once pinned, the server SHALL accept only UPDATEs whose SIG(0) verifies against the pinned key, or against a new candidate undergoing a valid rollover (KEY-03).§10.2
KEY-02A push signed by any other key SHALL be rejected with RCODE NOTAUTH.§10.2
KEY-03If the pinned key's SIG(0) fails but the UPDATE also carries a different candidate DNSKEY whose own SIG(0) verifies, the server SHALL attempt rollover by subjecting that candidate to the identical chain-of-trust check first contact requires (CHAIN-03..05).§10.4
KEY-04A rollover UPDATE SHALL NOT be required to carry an apex SOA.§10.4
KEY-05On successful rollover, the server SHALL replace the pinned key; the superseded key SHALL cease to authenticate further UPDATEs.§10.4
KEY-06The system SHALL use a single Ed25519 key as both SIG(0) transaction key and DNSSEC KSK; no KSK/ZSK split is required.§9.1 (design decision)

3.4 ALGO — Minimum algorithm floor

IDRequirementSource
ALGO-01A first-contact or rollover candidate key whose algorithm RFC 8624 §3.1 rates MUST NOT or NOT RECOMMENDED for zone signing SHALL be refused (REFUSED, status ERR_WEAK_ALGORITHM).RFC 8624 §3.1 · §10.7
ALGO-02The accepted set SHALL be an explicit allow-list — RSASHA256, ECDSAP256SHA256, ECDSAP384SHA384, ED25519, ED448 — with any unrecognised algorithm rejected by default.RFC 8624 §3.1
ALGO-03The algorithm check SHALL run before any SIG(0) cryptographic verification or chain-of-trust network activity for the candidate.Engineering decision

IDRequirementSource
CARRIER-01UPDATE messages SHALL be accepted over UDP and TCP.RFC 1035 · RFC 7766

3.9 SEC — Abuse & flood hardening

IDRequirementSource
SEC-01A first-contact or rollover attempt (the only operations triggering an outbound chain-of-trust network walk) SHALL be accepted only over a connection-oriented transport (TCP, HTTPS, HTTP/3); an attempt over plain UDP SHALL be refused (status ERR_TRANSPORT_NOT_ALLOWED).Engineering decision (spoofing hardening)
SEC-02A global, per-source-address rate limit on UPDATE attempts SHALL be enforced independent of the target zone, checked before SIG(0) verification; an excess SHALL be refused (status ERR_RATE_LIMITED).§12
SEC-03A per-zone daily quota on full-zone and differential pushes SHALL be enforced independently over a rolling 24-hour window; an excess SHALL be refused (status ERR_QUOTA_EXCEEDED).§12
SEC-04Rate-limiter internal state SHALL be periodically garbage-collected so memory is bounded by recently active keys, not by every distinct key ever observed.Engineering decision
SEC-05Rejections caused by SEC-01 or SEC-02 SHALL NOT be persisted to the audit trail.Engineering decision

3.11 WATCH — Delegation-change monitoring

IDRequirementSource

WATCH-03An alert SHALL fire only on a state transition (OK→failing or failing→OK) relative to the previous check, never on a zone's first-ever observation.§11
WATCH-04Alerts SHALL dispatch via SMTP for mailto: contacts and via an HTTP POST (JSON) for http(s):// contacts.§11

1 Test strategy

Verification is entirely automated Go tests (go test), run at three levels, from the same source tree as the implementation:

  • Unit — pure functions and small types in isolation (signature primitives, canonical-name ordering, algorithm tables, sliding-window counters).
  • Integration / end-to-end — a real dnsserver.Server, dnsserver.ServerHTTPS, or dnsserver.ServerHTTPS3 is started with the SAZU plugin installed, and a genuine SIG(0)-signed RFC 2136 UPDATE is sent over an actual UDP, TCP, or HTTP socket — not a direct function call into the handler. Chain-of-trust tests substitute a fake, deterministic ChainValidator for the real DNS-root walk (which chain.go's own dedicated tests cover against real network queries).
  • Manual / real-binary — a separately compiled coredns, sazuctl, and sazu-watchd, run against each other over real sockets (including real TLS for HTTPS), performed during development and re-summarised in the companion Test Report §5. Not part of the repeatable go test suite, and not re-executed for every change — recorded once, at the point each capability was verified working end to end.

Every test case below is traced to at least one requirement in the companion Requirements Specification, and every requirement is covered by at least one test case (§3 tables, column "Verifies").

6 Defects found and resolved during development

An honest retrospective. Every item below was found by the assistant's own testing discipline — running the full suite after each change — not reported by an external user, and every item was fixed before this report was produced.

#DefectImpact if shippedResolution
1An early refactor of the key-rollover flow in serveUpdate accidentally skipped SIG(0) verification entirely for first-contact pushes.Critical — would have allowed unauthenticated zone onboarding.Caught by full-suite failures; candidate-resolution flow restructured; regression covered by the existing AUTH/CHAIN test set.
2Global per-source-IP rate limiting did not exist; a scanning attacker could probe unlimited distinct zone names from one address, since each zone's own quota is independent.High — resource exhaustion / zone-discovery scanning at will.IPRateLimiter (§SEC-02) added, checked first in serveUpdate ahead of any chain-of-trust work.
3The new per-IP limiter (and the pre-existing per-zone limiter) keyed on data reachable over connectionless UDP, where the source address can be spoofed without completing a handshake.High — an attacker could exhaust a victim address's quota, or attempt to defeat the limiter's own accounting, by spoofing UDP source addresses; undermines SEC-02's purpose.connectionOriented gate (§SEC-01) added: first-contact and rollover attempts are refused outright over any non-connection-oriented transport (plain UDP), forcing an attacker to complete a real TCP/TLS/QUIC handshake first.
4Both sliding-window rate limiters accumulated one map entry per distinct key (zone name or source address) forever, with no eviction.Medium — unbounded memory growth under sustained scanning or churn, a slow denial-of-service against the server process itself.sweepIfDue (§SEC-04) added: both limiters garbage-collect entries older than one window, at most once per window, bounding memory to recently active keys.
5Every rejected update attempt, including the two rejection reasons above, was written to the audit-trail database — an attacker who could trigger cheap rejections (a malformed transport or exhausted quota) could grow the audit table without bound.Medium — unbounded disk growth, independent of the memory fix in item 4.Transport-gate and rate-limit rejections (§SEC-05) are explicitly excluded from audit-trail recording; genuine authentication/chain-of-trust failures remain fully audited, since those require real per-attempt cryptographic work by the attacker and are inherently self-limiting.
6The first hand-written test for the UDP-transport gate used BuildFullZonePush (SOA + NSEC + RRSIGs), producing a message over 512 bytes and tripping RFC 1035's UDP truncation before ever reaching the new gate — a false pass for the wrong reason.None (test-authoring issue, caught before merge).Discovered that containsAPEXSOA is checked after the chain-of-trust walk, meaning the smallest real attack packet needs only a DNSKEY-add + SIG(0). Rewrote using a new minimalFirstContactWire helper matching that minimal, realistic shape — a more accurate test of the actual threat.
